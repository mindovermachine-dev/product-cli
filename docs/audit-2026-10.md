# decision-cli audit against ledger-cli-prd.md

Audit date 2026-10-01. Read-only: no code changed. The only files this audit adds are this report
and its input, `docs/ledger-cli-prd.md` (Draft 1, 2 October 2026).

**What was audited, and why it is not the `decision-cli` repository.** The PRD targets "the
open-source `decision` CLI (decision-cli)". The ledger it describes is implemented here, in
`product-cli`, as the `ledger-core` and `ledger-cli` workspace members. The binary is `ledger`
(`ledger-cli/Cargo.toml` `[[bin]] name = "ledger"`) and the store is `.decisions/`
(`ledger-core/src/lib.rs` `STORE_DIR`). The repository `Hafeok/decision-cli` is a different tool:
the `dec` orchestration binary. Its only "ledger" files are dispatch-dedup ledgers
(`crates/dec-harness/src/subscriptions/*/ledger.rs`), and it has no decision format. Everything
below refers to `product-cli` unless it says otherwise.

**Documents the prompt asked for that do not exist.** There is no `ledger-authority.ttl`, no
`ledger-authority-shapes.ttl`, and no authority amendment in this repository, in
`Hafeok/decision-cli`, in `Hafeok/decision-driven-analyzers` or in `Hafeok/Varve`. None of them
contains the strings `accept-decision` or `ledger-authority`. The normative documents are:

- `docs/ledger-format-v1.md`: spec v1.5, formats 1–4.
- `docs/ledger-format-migrations.md`.
- The older product PRD, `docs/decision-ledger-prd.md`. Its §4.5 and its milestone L6 already rule on signing, and several of those rulings conflict with the new PRD (see §9).

**The samples.** Two kinds were read. The first is the repository's own store: `.decisions/` holds 2 sets and 187 change-sets. 154 of them declare `format: 1` and 33 declare `format: 3`. 91 acceptances are filed, all with `scope: version`. The second is the 11 fixture stores under `ledger-cli/tests/fixtures/` (`pass`, `l001`–`l008`, `l010`, `forked`, `two-clocks`, `coverage`).

The external inputs are `Hafeok/decision-driven-analyzers@HEAD` (`docs/rules/ledger-input.md`, `src/DecisionDriven.Analyzers/Ledger/NTriplesReader.cs`) and `Hafeok/Varve@acb802b` (`docs/decisions/*.md`).

## Summary

1. **What exists.** The ledger is a content-addressed, append-only YAML log. Change-sets live in `.decisions/log/<ulid>.yml` and sets in `sets/<id>.yml`. Version hashes are SHA-256 over canonical JSON. `verify` runs a closed file gate (SCHEMA + `L001`–`L010`) and a SPARQL graph stage (`G001`–`G005`). It has 18 verbs, including merge, diff, coverage and batched accept. The Turtle emission already uses `urn:ledger:ns#` and PROV-O.
2. **What the PRD changes.** The PRD adds:
   - a human key and an export flag on versions;
   - commit and citation nodes;
   - signed acceptances (SSH, RDFC-1.0) with a namespace policy and `allowed_signers`;
   - a role-gated, TTY-only `accept`;
   - a committed N-Triples export with freshness checking;
   - `review` and `import`;
   - one-act supersession that carries the key.
3. **Gap 1: no human identifier.** A decision is `dec:<ns>/<ULID>` and nothing else. `deny_unknown_fields` means no `key` can be smuggled in. Everything the generator, `review` and `import` need hangs on the key.
4. **Gap 2: no authority model.** No entity says who may accept. The only checks are:
   - `L006`: a heuristic that refuses model or bot identities;
   - `L009`: the git author email equals the claimed actor, and only once committed.

   Identity comes from `git config user.email`. Nothing signs, and nothing refuses a non-interactive caller.
5. **Gap 3: no export and no import.** Only a Turtle index exists, and it is gitignored. Its `ledger:set` is an IRI, where the analyzers' reader expects the set id as a literal. Nothing reads the interim Markdown. An import would have to invent the allocation (or fail `L001` 513 times on Varve), plus ULIDs, floors and set owners.
6. **The PRD's core claims hold.** It is right that acceptance must be signed and that the export must be a deterministic, committed artifact.
7. **Where the PRD is wrong about this design:**
   - It says "every entity is a file whose hash is its identity". Only versions are hashed.
   - It calls key immutability a file-gate check. It is cross-file.
   - It omits allocation and tolerance entirely.
   - It contradicts the principal's 2026-08-11 L6 rulings: the signed payload, tier gating, and the reservation of `L011`/`L012`.
8. **The first PR that can land without a format bump** is `ledger export --format ntriples` plus `verify --export` (§11).

The prompt asked for four behaviours to be established by reading, not guessing:

- **Can a version be created without a change-set?** No. A version exists only inside a change-set's `versions:` list (`changeset.rs` `ChangeSet`). Every verb builds one through `Author::shell` (`author/mod.rs:191`) and writes it through `Author::append` (`:175`), which refuses to overwrite. A hand-authored log file is still a change-set.
- **Can a non-holder create a change-set?** Yes, anyone can. There is no holder concept. `created_by` is whatever `git config` says, and a model identity is legal there by design. Test `ledger-cli/tests/verbs.rs:220` `a_model_identity_can_author_but_never_sign` pins it. In the real store, 94 change-sets are `created_by: noreply@anthropic.com`.

  - a forked chain;
  - a decision with no version;
  - a duplicate live acceptance;
  - for a batch: a held member or manifest drift.

## 4. Hashing

Only **decision versions** are content-addressed. Change-sets, acceptances and revocations are
identified by ULID, and their content is outside every hash (`ledger-format-v1.md` §4.1, "Outside
the hash").

**The exact serialisation currently hashed** (`ledger-core/src/canon.rs:70` `canonical_json`,
`hash.rs:89` `version_hash`):

1. Take the fields of `VersionRaw` in the hashed set:

   ```
   decision · parent · merged_from · set · statement · allocation · discharge ·
   discharge_stage · actor · expectation · exposure · accepted_by · review_by ·
   tolerance_floor_at_creation · tolerance_override · based_on · revisit_if · supersedes
   ```

   `hash` is bound and discarded. `scalar_fields` destructures **with no `..`**, so a new field fails to compile until someone classifies it.
2. Normalise each string with `canon::norm`: CRLF/CR → LF, then NFC, then trim ASCII whitespace. An empty string is treated as absent.
3. Omit any key that is absent, null, empty, or normalises to empty.
4. List fields (`discharge`, `based_on`, `revisit_if`) become **sets**: normalised, deduplicated, sorted by code point (`put_set`, a `BTreeSet`).
5. Emit compact JSON with keys sorted by code point, using `serde_json::Map` (a `BTreeMap`) and `Value::to_string()`. Escaping is serde_json's: `\" \\ \b \f \n \r \t`, `\u00XX` for other C0 controls, everything else as literal UTF-8. This matches RFC 8785 for ASCII keys and float-free content.
6. Every value is a string. Dates are `YYYY-MM-DD`; tiers, identities, ids and hashes use their `Display` forms. No timestamp is hashed.
7. Compute `"sha256:" + hex(SHA-256("ledger.decision-version.v1" ‖ 0x0A ‖ json_utf8))`.

Ordering is deterministic by construction (`BTreeMap`/`BTreeSet`). Determinism is pinned by:

- the conformance vector in format §4.4 (test `canon_tests.rs` `the_pinned_conformance_vector_holds`);
- the real hashes in the fixture stores (`gate.rs` `fixture_hashes_are_current`);
- the .NET twin's shared digest fixture `docs/eval-format-v1/context-digest.json`, which rides the same `canon` primitives.

The workspace rule in `CLAUDE.md` is explicit: "one hashing law in this workspace, never a
second scheme". `domain_hash(prefix, bytes)` exists so new payloads reuse the law under their own
prefix. Examples are `ledger.acceptance-manifest.v1` in `batch.rs`, and `spec.act-record.v1` and
`eval` in other crates.

**This is a bespoke serialisation, not RDFC.** RDF never enters the hash path. The Turtle emitter
(`graph/turtle.rs`) is downstream of the hash and outside the format's import surface.

**Can the two coexist without a format break?** Yes, on the version side. The PRD signs the
*acceptance*, and acceptances are outside the version hash, so no digest moves and
`CANONICAL_FORM` stays `v1`. The older PRD's §4.5 makes the same point. Three caveats must be
settled first; §9 argues each:

- **There is no acceptance hash today.** The PRD's "acceptance hash covers content, not signature" introduces a second content-addressed entity. It needs its own prefix (for example `ledger.acceptance.v1`). That is additive, but it is a new entity identity scheme.
- **"The acceptance node's triples" is not stable.** The emitter puts revocation triples on the acceptance IRI (`turtle.rs:221` `emit_revocation` → `<urn:acc:…> ledger:revokedAt …`), as the analyzers' reader expects. RDFC over "the node's triples, excluding `ledger:signature`" would include triples appended later by a revocation, so every revoked acceptance's signature would stop verifying. The signed triple set has to be a closed predicate list, not "the node".
- **RDFC makes the RDF mapping normative.** IRI minting (`urn:acc:`, `urn:sha256:`, `mailto:`), the literal datatypes (`xsd:dateTime` with `SecondsFormat::Secs`), and the predicate vocabulary are reference-implementation details today. Signing over them pulls all of it into the import surface. It also means a second canonicalisation law beside `canon`.

## 5. Export

**What exists.** `ledger reindex` writes `.decisions/index/ledger.ttl` through `graph::turtle::emit`
(`turtle.rs:93`). It is deterministic: subject → predicate → object in `BTreeMap`/`BTreeSet` order.
A byte-identical rebuild is tested (`ledger-cli/tests/graph.rs:43`). But it is:

- **Turtle**, not N-Triples. It uses `@prefix` lines, prefixed names, `a`, `;` continuations and `xsd:` CURIE datatypes.
- **Gitignored** (`init.rs` `IGNORE_LINE = ".decisions/index/"`), so it is never committed.
- **Whole-store.** There is no namespace selection and no exported-only filter.
- **Escaped only partly.** `literal()` escapes `\\ " \n \r \t` and leaves other C0 controls raw. That is legal N-Triples, but not canonical N-Triples, which requires `\b \f` and `\uXXXX` for the rest.

It includes acceptances and revocations. It omits `signature` (always empty), and it has no policy
or signer snapshot.

`verify --export` becomes "re-emit and compare bytes". One exception: the PRD's `ledger:Commit`
nodes would make the export a function of **git history**, not of the log alone. That breaks the
property the current rebuild test protects, and it makes an export taken before the commit differ
from one taken after (§9, C6).

## 6. Identity

**Are identities `mailto:` IRIs everywhere?** No.

- On the wire, an identity is a **bare, lowercased email** (`identity.rs:103` `FromStr`). The format says so in §3.2.
- `mailto:` appears **only in the RDF emission** (`turtle.rs` `mailto()`).
- The parser does **not** reject a scheme prefix. `mailto:emil@okkels-klein.dk` parses as an identity whose local part is `mailto:emil`: one `@`, no whitespace, so it passes. It is then a *different* identity from `emil@okkels-klein.dk`, and it would emit as `<mailto:mailto:emil@…>`.

This matters for `import`. All 513 Varve acceptances spell the actor with the `mailto:` prefix.

**The "model is not a holder" check.** This is `L006`, on acceptance actors and escape acceptors,
and `L010`, on judgment actors, both through `Identity::model_or_bot_reason` (`identity.rs:69`). It
decides by denylist:

- vendor no-reply addresses;
- `[bot]`;
- `github-actions.*` domains;
- reserved local parts (`ci`, `bot`, `noreply`, …);
- whole-token model names in the local part (`claude`, `gpt`, `copilot`, `agent`, `ai`, …).

The format doc calls this "a floor, not a proof" (§3.2). It does not check:

- `created_by` (models may author, by design);
- a revocation's `by` (§3);
- `actor:` discharge pointers (format §6).

Because "holder" means only "not obviously a machine", a model configured with a human address
passes `L006`. If it also commits under that address, it passes `L009` too.

**Does anything sign?** Nothing signs files or acceptances. `signature` is forced empty. The CLI
signs no commits, because it makes none. Commit signing is whatever the user's git does. One
caveat in the test helpers: `blame_tests.rs` commits with `--no-gpg-sign`. The format's own
position is that `L007` (tamper), `L008` (pairing) and `L009` (git authorship) "stand in for a
signature at L0" (`verify/integrity.rs` module doc).

**Non-interactive operation.** The CLI runs non-interactively everywhere and refuses it nowhere:

- No `isatty`/`IsTerminal` check exists in `ledger-core` or `ledger-cli`.
- `accept <id>` writes at once.
- The batch path's dry run → `--confirm <manifest>` is a two-step flow that a script can run end to end: run once, parse `"manifest"` from `--json`, run again.
- `merge --resolve` reads stdin (`resolve_cmd.rs`). At EOF it resolves nothing, so it fails safe, but it does not refuse a non-TTY.

To refuse non-interactive use, `accept` would need a terminal check on stdin *and* on the signing
prompt. That check cannot be bypassed by an environment variable without becoming the agent's
bypass. The test harness (`assert_cmd`, no PTY) therefore has to move to a PTY driver, or test
the core with an injected interactivity predicate.

## 9. Contradictions between the PRD and the current design

**C1. "Every entity is a file whose hash is its identity" (PRD §2).**
- **The PRD assumes:** one file per entity, named by its hash.
- **The code does:** one file per *act* (a change-set holding decisions, versions, acceptances and revocations), named by ULID. Only versions are content-addressed. Acceptances are `acc:<ULID>`.
- **Which should give way:** the PRD. Change-set grouping is a principled choice: "one act touches 4 of 200" (`changeset.rs` doc). It is what makes batched accept produce *one* reviewable file of N records, and what makes `L009` attribution per act. Hashing acceptances is still worth doing for signatures, as a new content identity (`ledger.acceptance.v1`) alongside the ULID, not instead of the file layout.

**C2. Key immutability is a "file gate" check; key uniqueness is a "graph stage" check (PRD §4).**
- **The PRD assumes:** the file gate is single-file and the graph stage is cross-file.
- **The code does:** the file gate is the **format's import surface** and is already cross-file (`L005`, `L008`). The graph stage is explicitly optional for outside implementations (format §8).
- **Which should give way:** the PRD's placement. Both key rules are what make generated C# type names stable, and the Org Ledger and any other importer must enforce them. They belong in the file gate as new L-classes by the `L010` amendment mechanism. Uniqueness may *also* have a SPARQL shape, but it cannot be graph-only.

**C3. The PRD's decision has no allocation, tolerance or discharge.**
- **The PRD assumes:** a decision is key + statement + acceptances, and import and `new` need nothing else.
- **The code does:** allocation is the format's centre (`L001`, `L002`, `L010`), and tolerance floors are pinned per version (`L004`, `L005`).
- **Which should give way:** the PRD has to state the allocation story. Dropping `L001` would gut the gate the CI step exists for. For the analyzers' use (citable architectural rulings), `constraint` with an analyzer discharge is plausible. That is a ruling for the principal, and an importer must not invent it. A permitted alternative is to let import write unallocated decisions *only* in a set whose policy declares "allocation pending", which is a new state the format would have to name.

**C4. The signed payload: "RDFC-1.0 of the acceptance node's triples" (PRD §7) versus the ruled payload in `decision-ledger-prd.md` §4.5 ruling 1 (decision id, version hash, actor, signing timestamp).**
- **The PRD assumes:** the RDF node is a stable unit to canonicalise.
- **The code does:** revocation triples land on the acceptance node (`emit_revocation`), so "the node" changes after signing. The RDF mapping is non-normative. Workspace policy is one hashing law (`canon` + `domain_hash`).
- **Which should give way:** both, partly. The PRD is right that **scope** (and `expires_at`) must be signed. The ruled payload omits them, so a `class:` acceptance could be re-scoped without breaking the signature. The PRD is wrong to sign "the node".

  Recommendation: sign a closed acceptance payload `{decision, version, actor, at, scope, expires_at}`, canonicalised by the existing JSON law under a new prefix. `ssh-keygen -Y sign` operates over those bytes, and `ssh-keygen -Y verify` still validates independently, which meets PRD §10 bullet 2. The export carries every payload field as a triple, so an export-only verifier can rebuild the bytes. If RDFC is kept, the format doc must make the IRI and literal mapping normative and list the signed predicates. Either way, this is the principal's open L6 sub-question ("whether the signature payload reuses §4's canonicalisation or takes a distinct domain-separation prefix") and has to be ruled, not decided by the PRD.

**C5. Everything signed under namespace policy (PRD §5, §7) versus tier gating (older PRD §4.5 ruling 3: T2 signed, T1 claimed).**
- **The PRD assumes:** policy decides per namespace.
- **The code does:** nothing yet, but the principal ruled tier gating on 2026-08-11.
- **Which should give way:** neither; the two compose. Make policy the mechanism and the tier its default predicate ("signature required at effective tier ≥ X"). The up-only floor then keeps the requirement from being shopped out, which is the property ruling 3 cares about. The PRD should not silently supersede a recorded ruling.

**C6. `ledger:Commit` nodes in the export (PRD §4, §8), and "everything reproducible from the repository alone" (PRD §2).**
- **The PRD assumes:** commits are data the export can carry.
- **The code does:** derived artifacts are functions of the **log**, and the rebuild test enforces byte identity from the log alone. Commit SHAs change on rebase or squash. A change-set has no commit until it is committed, so an export written in the same PR as the change-set cannot name its own landing commit.
- **Which should give way:** the PRD's placement of the commit node. Keep commit nodes in the **citation projection** (the analyzers' report, which runs over history) and in a separate history export. Keep them out of the export that `verify --export` byte-compares, or freshness can never pass on the PR that introduces the entry.

**C7. Identity: `mailto:` IRIs "everywhere" (PRD §2) versus bare emails on the wire (format §3.2).**
- **Which should give way:** neither needs to. The RDF side already uses `mailto:`. The wire form should stay bare, since adding the scheme to hashed `accepted_by`/`actor` would move digests. The parser should **reject** a scheme prefix instead of accepting `mailto:x@y` as a distinct identity (§6).

**C8. Accept: direct multi-key with a TTY prompt (PRD §5, §6) versus dry-run plus manifest (`accept --set|--group`).**
- **The PRD assumes:** one TTY confirmation per key is the deliberateness device.
- **The code does:** the manifest binds *what was read* to *what is signed* and refuses on drift (`batch.rs`), and a held member stops the run.
- **Which should give way:** the PRD should add the TTY and key-touch on top, not replace the manifest. A TTY prompt proves a human is present, but not that the selection did not move between `review` and `accept`. The PRD §6 loop (review → accept) is exactly the read-then-sign gap the manifest closes.

**C9. One-act supersession that creates the successor (PRD §5) versus the two-step `add` + `supersede --by`.**
- **Which should give way:** the code. With keys, the two-step form makes the successor briefly live with either no key or a duplicate key, which violates uniqueness among live decisions in the very act that is meant to carry the key. A single change-set holding the new decision, its first version and its `supersedes` edge is the clean fix. `G005` stays as the cross-branch backstop.

**C10. `decision revoke <key>` revokes "the tip's acceptances" (PRD §5) versus revoking one acceptance by id.**
- **Which should give way:** the PRD, partly. Bulk revocation of every holder's acceptance by one actor is an authority question the PRD does not answer. Today *anyone, including a model,* can revoke *anyone's* acceptance, because the revoker is unpoliced (§3). That gap is real and should close first: a revoker must pass `L006` and hold the role, or be the original acceptor.

**C11. Command name `decision`, directory `ledger/`, repository "decision-cli".** The binary is `ledger`, the store is `.decisions/`, and `Hafeok/decision-cli` is the `dec` orchestrator.
- **Which should give way:** the PRD. Renaming would churn the format doc (which fixes `.decisions/`), the CI step, the merge driver's `.gitattributes`, and every test, for nothing. Keep `ledger` and `.decisions/`. The analyzers' README ("until `decision export` exists") should say `ledger export`. The export output path (`docs/decisions/<ns>.nt`) is a separate choice and is fine.

**C12. Items the PRD calls out of scope (§9) that exist as plans here, not as code.**
- The older PRD's L6 includes the **X.509 path as "the bridge to the org product, where Entra-issued certificates"** plus the `gpg.format` trio. The PRD calls CA integration a non-goal and ships `ssh` and `none` only.
- The older PRD's L5 workbench is a **local-first web app**. The PRD calls a web UI a non-goal.
- L4 `fetch <remote-namespace>` is borderline: offline, git-based, not a service.

None of these has code, so nothing needs removing. The older PRD's L5 and L6 rows should be amended to match, or the new PRD should say it supersedes them.
